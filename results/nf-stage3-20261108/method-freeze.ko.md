# 새 입력 열계산 전 확정한 세 탐색 방법

이 결정에는 개발 방전 `1a3155370c`의 1400 ms만 사용했다. 12개 새 입력의 순번·시각 및 결측 판정은 [등록 자료](inputs/registration.json)에 고정했다. 실행 방법은 [원래 계획](protocol.ko.md)과 아래 설정을 따른다.

| 방법 | 제안과 정밀 채택 |
|---|---|
| floor-screened | 바닥 4계수. 끝점 접선 조건에 투영한 초기 형상 및 재시작, 현재 실행의 상위 형상 주변 교란. cubic320 저비용 평가를 묶어서 수행하고 cubic1280에서 확인한 적격 후보만 채택한다. |
| full-screened | 같은 선별·채택 규칙에 비바닥 12계수를 추가한다. 제안에는 바닥만 움직이는 경우도 포함된다. |
| full-direct | 전체 16계수. 각 새 프로세스는 과거 형상 없이 시작한다. cubic1280 평가로 직접 갱신하는 32개체 차분진화(DE)를 사용한다. 바닥 투영을 12번 시도하고 공간 교란을 섞어 초기화하며 첫 집단의 affine rank 16을 검사한다. 기존 OMP DE의 즉시 갱신, 19번째 제안마다 가능한 좌표 정련, 정체 시 재시작을 유지한다. 같은 실행 내 중복 제안은 이전 점수를 재사용한다. |

전체 선별 대 전체 직접의 비교 대상은 **각각의 제안 방식과 평가 방식을 결합한 탐색 절차**다. 이 차이에서 선별 단계만의 인과적 기여를 추정하려면 같은 제안기를 사용한 별도 대조군이 필요하다. 정밀 적격 판정과 전 벽 피크 목적은 세 방법에서 같다. 제약으로 기각된 제안은 시간과 시도 횟수에 포함하고 실제 열계산 여부는 별도로 기록한다. 기본 CLI는 기존 선별 방법을 사용한다. [직접 탐색](../../d3d_optimization/user_direct_search.py) · [선별 탐색](../../d3d_optimization/user_search.py)

## 개발 방전 시운전

RTX 3090, 시드 20711, 예산 600초. 140.80초에 원벽 평가를 마쳤고 141.05초에 초기 집단이 16차원을 모두 차지했다. 419.43초에 첫 DE 시도를 시작했고 455.88초에 적격 열계산을 마친 첫 DE 시도가 나왔다. 475.08초에 초기화 이후 첫 세대의 32개 표적을 모두 평가했다. DE 정밀 요청 55개 중 6개가 시한 안에 실제 열계산까지 마쳤고 5개가 적격이었다. 마지막 지연 평가는 611.32초에 끝나 채택에서 제외됐다.

이 개발 예의 전체 최저는 초기화에서 198.03초에 나왔다. 원벽 2.730756에서 1.900560 MW/m²였다. 32개체·투영 12회 설정을 그대로 확정한다. 이 개발 예는 이후 적중률이나 방법 간 비교의 분모에서 제외한다. [검증 수치 및 해시](commissioning.json) · [시도별 기록](commissioning/events.jsonl) · [개발 예 결과](commissioning/result.json)

## 계시와 실행 기록

공개 CLI 진입 직후부터 입력 처리·원벽·후보 계산에 사용된 시간을 센다. 새 Python 프로세스는 표준 라이브러리로 계획 해시와 동시 실행 잠금을 검사한 뒤 CLI를 호출한다. 작업별 기록에는 CLI 호출 경과를 남기고, 부모 프로세스는 작업자 생성부터 종료까지를 `observations/`에 별도로 기록한다. 두 시각의 범위는 다르다. 완료한 CLI 결과가 남아 있는 중단 작업은 저장된 결과를 복구하고, 복구할 수 없는 종료코드나 경과는 결측으로 보존한다. 원자료와 실행 환경은 [등록 자료](inputs/registration.json)와 [환경 기록](execution-environment.json)에서 확인할 수 있다.
